## 1. 문제 정의

초기 구현은 **웨이포인트마다 완전히 멈췄다가 다음으로 출발**했다.

```
P5 ──▶ [정지] ──▶ P2 ──▶ [정지] ──▶ P1 ──▶ [정지] ──▶ ...
```

이유는 안전 때문이었다. 완료 판정을 이렇게 했다:

```python
목표 near_deg 이내  AND  연속 confirm_n회 정지  AND  check_motion 유휴
```

**왜 이렇게 엄격했나 (실측 교훈):**

| 사고 | 원인 |
|---|---|
| 사이클이 로봇 없이 혼자 진행 | `movej` 응답을 확인하지 않음 → 거부됐는데 다음 단계로 감 |
| 급정지 '쿵' + 노란불 | '정지'만으로 완료 판정 → **감속 크리프 구간에서 조기 완료** → 이동 중 다음 명령 = 명령 충돌 |
| 공 쥔 채 토크 스파이크 | 40N으로 공을 쥔 채 빠르게 감속 → 펜던트 안전한계 침범 |

즉 **안전을 위해 정지를 넣었지만, 그 대가로 동작이 뚝뚝 끊겼다.**
한 사이클에 정지가 10회 이상 발생했고, 특히 **모든 흐름이 지나가는 허브 P5**에서 매번 섰다.

**목표**: 안전 판정은 유지하면서 경유점에서의 정지를 없앤다.

## 2. 방법 A — radius 블렌딩

두산이 제공하는 **공식 블렌딩**이다. `MoveJoint.srv`를 보면:

```
float64[6] pos          # 목표 관절각 [deg]
float64    vel          # 속도 [deg/s]
float64    acc          # 가속도 [deg/s²]
float64    time         # 시간 [s]
float64    radius       # ★Radius under blending mode [mm]
int8       mode         # ABSOLUTE=0, RELATIVE=1
int8       blend_type   # DUPLICATE=0, OVERRIDE=1
int8       sync_type    # SYNC=0, ASYNC=1
```

### 원리

경유점 주위에 **반경 R의 가상 구(sphere)** 를 놓고, 로봇이 그 구에 들어오면
경유점에 정확히 닿지 않고 **호를 그리며** 다음 목표로 넘어간다.

```
        경유점 P
           ●
      ╭────┼────╮        radius = R
     ╱     │     ╲       실제 궤적은 P를 통과하지 않고
    │   R  │      │      이 원 안에서 부드럽게 꺾인다
     ╲     │     ╱
      ╰────┼────╯
    ───────┴──────▶
```

### blend_type 두 가지

| 값 | 이름 | 의미 |
|---|---|---|
| 0 | `DUPLICATE` | 앞 이동의 속도 프로파일을 **유지**하며 겹침 |
| 1 | `OVERRIDE` | 뒤 이동의 속도로 **덮어씀** |

### 필수 조건 — 여기가 함정이었다

블렌딩은 **두 명령이 시간적으로 겹쳐야** 성립한다.
따라서 첫 명령이 **끝날 때까지 기다리면 안 된다** → 반드시 **`sync_type = 1` (ASYNC)** 이어야 한다.

`sync_type=0`(SYNC)은 도착할 때까지 블로킹하므로 겹칠 수가 없다.

**그런데 바로 이 조합에서 radius가 사라진다.**

## 3. radius가 안 되는 이유

### 드라이버 소스 직접 추적

`src/doosan-robot2/dsr_controller2/src/dsr_controller2.cpp` **431~445행**:

```cpp
auto movej_cb = [this](const std::shared_ptr<dsr_msgs2::srv::MoveJoint::Request> req, ...)
{
    ...
    if(req->sync_type == 0){                                    // ── SYNC 경로
        res->success = Drfl->movej(target_pos.data(), req->vel, req->acc, req->time,
                                   (MOVE_MODE)req->mode,
                                   req->radius,                 // ★radius 전달됨
                                   (BLENDING_SPEED_TYPE)req->blend_type);
    }
    else{                                                       // ── ASYNC 경로
        res->success = Drfl->amovej(target_pos.data(), req->vel, req->acc, req->time,
                                    (MOVE_MODE)req->mode,
                                                                // ★radius 인자가 아예 없다
                                    (BLENDING_SPEED_TYPE)req->blend_type);
    }
};
```

### 결론

| 경로 | radius | 블렌딩 가능? |
|---|---|---|
| `sync_type=0` → `Drfl->movej(..., radius, ...)` | ✅ 전달됨 | ❌ **불가** — 도착까지 블로킹이라 겹칠 수 없음 |
| `sync_type=1` → `Drfl->amovej(...)` | ❌ **인자 자체가 없음** | 겹침은 되지만 radius가 없어 호가 안 생김 |

> ### 💡 핵심 발견
> **`radius`는 이 드라이버에서 도달 불가능한 파라미터다.**
> 값을 아무리 넣어도 async 경로에서는 조용히 버려진다.
> `blend_type`은 전달되지만 radius가 0이면 블렌딩 자체가 성립하지 않는다.

이걸 모르고 `radius=30`을 넣었을 때 **아무 변화가 없어서** 한참 헤맸다.
로그에 거짓 반경을 기록하지 않도록, 지금 코드는 **명시적으로 `req.radius = 0.0`** 을 넣고
주석으로 이유를 남긴다:

```python
# dsr_controller2의 amovej(async)는 radius 인자를 받지 않는다.
# 거짓 반경값을 기록하지 않고, 중간 전환은 wait_lead 시점의 다음 명령이 담당한다.
req.radius = 0.0
req.mode = 0                        # 절대각 — 오차 누적 없음
req.blend_type = 0; req.sync_type = 1   # 비동기(즉시 반환)라야 블렌딩
```

## 4. 방법 B — lead_deg 각도 기반 블렌딩

### 발상의 전환

radius를 못 쓴다면, **코너를 만드는 다른 변수**는 무엇인가?

async 명령은 **덮어쓰기(override)** 가 된다. 즉 이전 이동이 끝나기 전에 새 `amovej`를 보내면
로봇은 **감속하지 않고 새 목표로 방향을 튼다.**

> **그렇다면 "언제 보내는가"가 곧 "얼마나 크게 도는가"다.**

```
경유점 P 에 가까울 때 명령 → 작은 코너 (경유점에 바짝 붙어 돎)
경유점 P 에 멀 때   명령 → 큰 코너   (많이 잘라 크게 돎)
```

### 구현 — `wait_lead()`

```python
def wait_lead(via, lead=None):
    """경유점에 '충분히 가까워질 때까지' 기다렸다가 True 반환 — 다음 명령 투입 시점."""
    ld = float(cfg.BLEND.get('lead_deg', 12.0) if lead is None else lead)
    t0 = time.time()
    tmo = float(cfg.BLEND.get('lead_timeout_s', 30.0))
    while time.time() - t0 < tmo:
        chk()
        c = ctx.joints()
        if c and len(c) == 6:
            if max(abs(via[i] - c[i]) for i in range(6)) <= ld:   # ★남은 관절거리
                return True
        time.sleep(0.02)
    return False        # 타임아웃 — 그래도 다음 명령을 보내 진행(정지 후 이동일 뿐)
```

**판정 기준은 `max(|목표 − 현재|)`** — 6축 중 가장 많이 남은 관절의 각도다.
20ms 간격으로 관절 토픽을 확인하므로, 60°/s로 이동해도 약 1.2° 해상도로 잡힌다.

### 체인 실행 구조

```python
for i in range(at[0], len(steps)):
    tgt, mk = steps[i][0], steps[i][1]
    lead_i  = steps[i][2] if len(steps[i]) > 2 else None    # 구간별 코너 각도
    last    = (i == len(steps) - 1)
    at[0]   = i                                # 재개 기준점(12장 참조)

    req.mode = 0            # 절대각 — 재전송해도 중복 이동 없음
    req.sync_type = 1       # ASYNC — 즉시 반환해야 겹침
    ctx.call(ctx.cmj, req)  # amovej 발사

    if not last:
        wait_lead(tgt, lead_i)    # ★경유점에 lead_i° 남았을 때 다음 명령
# 마지막 점만 정식 도착 판정(near + still + check_motion)
wait_arrival(steps[-1][0])
```

### 이 방식의 장점

| | |
|---|---|
| ✅ | 드라이버 수정 없이 **지금 당장** 동작 |
| ✅ | **구간마다 다른 코너**를 줄 수 있다 (radius는 명령당 하나) |
| ✅ | 절대각(`mode=0`)이라 **오차 누적이 없다** — 재전송해도 안전 |
| ✅ | 중간 경유점은 도착 판정을 생략해 **대기 시간 0** |

### 한계 (정직하게)

| | |
|---|---|
| ⚠️ | 진짜 원호가 아니라 **컨트롤러의 명령 덮어쓰기**에 의존한다 |
| ⚠️ | 중간 경유점 **도달 검증을 못 한다** (통과해버리므로) → 그래서 **순수 통과용 경유점에만** 써야 한다 |
| ⚠️ | 20ms 폴링 지연만큼 코너가 미세하게 커진다 |

## 5. 방법 C — MoveSplineJoint

여러 점을 **한 명령으로** 컨트롤러에 넘겨 진짜 곡선을 그리게 한다.

```python
req = ctx.MoveSplineJoint.Request()
req.pos = [P5_점, next_lift_점]      # Float64MultiArray 리스트
req.pos_cnt = 2
req.vel = [v] * 6
req.acc = [a] * 6
req.mode = 0            # 절대각
req.sync_type = 1
```

**장점**: 컨트롤러가 직접 보간하므로 **가장 부드럽다.** 명령 타이밍에 의존하지 않는다.

**결정적 한계**: **스플라인은 끝점에서 반드시 완전 정지한다.**
따라서 "무정지로 통과"시키려면 그 점을 **끝점이 아닌 중간점**으로 넣어야 한다.

그래서 사이클 경계 P5를 없앨 때만 제한적으로 썼다:

```
[P5, next_lift] 두 점을 한 명령으로 → P5는 중간점이므로 무정지 통과
                                      next_lift 에서만 정지
```

> ⚠️ **슬롯 하강(P20/P3)은 절대 스플라인에 넣지 않는다.** 실기에서 문제가 있었다.
> 하강은 독립된 단일 MoveJ여야 슬롯 진입 경로가 곡선에 먹히지 않는다.

## 보완 ① 고정시간 → 각도 판정

### 사고

처음엔 단순하게 **고정 시간**으로 다음 명령을 보냈다.

```python
send(amovej, P5)
time.sleep(0.25)      # ← 0.25초 뒤 다음 명령
send(amovej, P2)
```

**증상**: 짧은 구간은 괜찮은데, **긴 구간에서 경유점을 통째로 건너뛴 것처럼** 보였다.

### 원인 — 계산해 보니 명확했다

```
P12 → P5 구간 = 115.6°,  속도 60°/s
0.25초 동안 이동한 각도 = 15°
→ 전체의 13% 지점, 즉 목표까지 아직 101° 남은 곳에서 방향을 틀어버림
```

**이동 거리에 따라 전환 지점이 제각각**이 되는 게 근본 문제였다.

### 해결

**시간이 아니라 "남은 각도"로 판정**한다. 어느 구간에서든 코너 크기가 일정해진다.

```python
if max(abs(via[i] - c[i]) for i in range(6)) <= lead_deg:
    다음 명령 투입
```

> 📌 **교훈**: 블렌딩 파라미터는 **거리(각도) 기준**이어야 한다. 시간 기준은 속도·거리에 흔들린다.

## 보완 ② 가속도 병목 제거

### 사고

속도 탭에서 **60°/s로 설정했는데 실제로는 약 21°/s**밖에 안 나왔다.

### 원인 — 삼각 프로파일

```
가속도가 낮으면 최고 속도에 도달하기 전에 감속을 시작해야 한다
        속도 ▲
             │      ╱╲            ← 삼각 프로파일: 설정 속도에 도달 못 함
        60 ┄ ┼ ┄ ┄ ╱ ┄╲┄ ┄ ┄
             │    ╱    ╲
        21 ┄ ┼ ╱        ╲        ← 실제 도달 최대치
             └──────────────▶ 시간
```

당시 가속도 상한이 구간별로 **12~30 deg/s²** 였다. 짧은 구간일수록 심했다.

### 해결

가속도 상한을 전부 **60**으로, 가속 비율을 **1.0**으로 올렸다.
가속도가 속도에 **비례**하게 만들어, 속도를 올리면 가속도도 같이 올라가 체감이 1:1이 되게 했다.

```python
a = max(cfg.SPEED['cycle_min_acc'],          # 하한 10
        v * cfg.SPEED['acc_ratio'])          # 비율 1.0 → a = v
```

| 항목 | 이전 | 현재 |
|---|---|---|
| `free_acc_max` 등 전 구간 | 12 ~ 30 | **60.0** |
| `acc_ratio` | < 1 | **1.0** |
| `acc_ratio_carry` | < 1 | **1.0** |
| 실제 도달 속도 | ~21°/s | **설정값 그대로** |

> 📌 **교훈**: "속도가 안 나온다"의 절반은 가속도 문제다. 둘은 같이 올려야 한다.

## 보완 ③ 사이클 경계 없애기

### 문제

공을 놓은 뒤 **P5로 복귀해서 멈췄다가** 다음 사이클을 시작했다.
공 3개를 처리하면 P5 정지가 **3회** 발생한다. 눈에 띄게 서 있었다.

```
[사이클1] ... P6 → P5 [정지] 
[사이클2]     P5 → P2 → P1 ... P6 → P5 [정지]
[사이클3]     P5 → P2 → P1 ...
```

### 해결 — `chain_cycles`

"다음에 무엇을 집을지"를 **미리 알고 있으므로**, 놓기 직후 다음 파지 경유지까지 **한 흐름으로 이어붙인다.**

```
P16 → ⊙P15 → ⊙P5 → P2      (⊙ = 무정지 통과)
```

사이클 사이의 P5 정지가 사라졌다. 뚜껑 열기↔작업 시작, 작업 끝↔뚜껑 닫기 경계도 같은 방식으로 병합했다.

## 보완 ④ 스플라인 + amovej 충돌 사고

### 사고 — 가장 위험했던 문제

P5 무정지 통과를 위해 스플라인을 쓰면서, **끝점 도착 전에 미리 다음 명령을 보내는** 최적화를 시도했다.

```python
send(MoveSplineJoint, [P5, next_lift])
wait_lead(next_lift, 10°)        # 10° 남았을 때
send(amovej, 하강목표)            # ← 스플라인 실행 중에 새 모션 투입
```

**증상**:
- 로봇이 **알람 없이 정지**
- 노란불(보호정지)이 아니라 **흰불** — 어떤 에러도 안 뜸
- 배치는 `슬롯 하강 도착 미확인`으로 중단

### 원인

실기 컨트롤러가 **스플라인 실행 중 들어온 새 모션**을 충돌로 판단해 내부적으로 정지시켰다.
알람 코드조차 남기지 않아 원인 추적이 어려웠다.

### 해결

**스플라인이 끝점에 도착한 것을 확인한 뒤에만** 다음 명령을 보낸다.

```python
# ★스플라인이 lift에서 끝나는 것을 확인한 '뒤에만' 하강을 보낸다.
#   (舊: 10° 남은 시점에 amovej 선행 전송 → 실기 컨트롤러가 스플라인 실행 중
#    새 모션을 충돌로 판단해 알람 없이 정지(흰불) → '도착 미확인' 배치중단)
#   quick 검증이라 대기는 ~0.3s — 스플라인 끝의 자연 감속과 겹쳐 체감 정지 없음.
if not wait_arrival(next_lift, quick=True, timeout_s=timeout_s):
    msg('⑨ 경유지 재조준(스플라인 종료 오차)')
    goto(next_lift, 'free', quick=True, move='ord_to_lift')
goto(next_pick, 'approach', move='ord_descend')
```

`quick=True` 도착 판정(확정 1회·유휴 1회·정착 0초)을 써서 대기를 **약 0.3초**로 줄였고,
이는 스플라인 끝의 자연 감속과 겹쳐 **체감상 정지가 없다.**

### 그 결과 — 현재 기본값은 스플라인 OFF

```python
'return_spline': False,
```

`amovej → amovej` 덮어쓰기는 이 로봇에서 무정지 전환이 검증됐고 모션 충돌도 없다.
**충돌은 '스플라인 실행 중 amovej' 조합에서만** 발생했다.
그래서 안전한 **순수 amovej 체인**을 기본으로 쓴다.

> ⛔ **절대 규칙: `MoveSplineJoint` 실행 중에 `amovej`를 겹쳐 보내지 말 것.**

## 보완 ⑤ 구간별 코너 각도 튜닝

radius 방식과 달리 **구간마다 다른 코너**를 줄 수 있다는 점을 최대한 활용했다.

### 최종 튜닝값

| 구간 | 값 | 근거 |
|---|---|---|
| **P5 출입** (`lead_deg_hub`) | **45°** | 사방이 트여 있어 크게 돌아도 안전 → 가장 부드럽게 |
| 일반 경유점 (`lead_deg`) | **25°** | P9, P13/P15 등 |
| **슬롯 위** (`lead_deg_slot`) | **18°** | P2/P4 — 슬롯 진입이라 정교해야 함 |
| 폐기물 기본 (`waste_lead_deg`) | **15°** | P25·P27·P29 |
| 폐기물 허브 (`waste_lead_hub`) | **25°** | P5·P28(버리러 갈 때) — 여유 구간 |
| **폐기물 복귀 P29** (`waste_lead_tight`) | **4°** | ⚠️ 아래 참조 |

### P29 특수 처리 — "속도가 아니라 경로가 문제"

폐기물을 버린 뒤 **역순으로 복귀**할 때 P29를 벗어나는 첫 부분에 **걸리는 구조물**이 있었다.

처음엔 속도를 낮춰 해결하려 했으나, 원인은 **코너를 자르면서 티칭 경로를 이탈**하는 것이었다.

→ **속도는 그대로 두고 P29 코너만 4°로** 줄여 티칭 경로를 바짝 따라가게 했다.
정지시키지는 않으므로 흐름은 유지된다. P28부터는 정상 코너로 부드럽게 이어간다.

```python
chain([(W['waste_drop'], 'waste_dump', 4.0),      # P29 — 바짝
       (W['waste_pre'],  'waste_carry'),          # P28 — 정상
       (W['waste_lift'], 'waste_carry'),
       (W['waste_pick'], 'waste_near')])
```

> 📌 **교훈**: 부딪히면 속도부터 낮추기 쉽지만, **경로 이탈이 원인이면 속도를 낮춰도 부딪힌다.**
> 코너 각도를 줄이는 게 정답이었다.

### ⛔ 회피용 경유점은 체인에 넣지 않는다

```python
# ★중간 경유점은 반드시 '순수 통과용'이어야 한다. 충돌 회피용으로 티칭된
#   경유점(P2/P4 슬롯진입, P13/P15 보충접근, P12→P10 뚜껑안착)을 넣으면
#   코너를 자르면서 회피가 무효가 되어 충돌한다.
```

블렌딩은 **정의상 경유점을 잘라낸다.** 그 점이 "장애물을 피하려고" 찍은 점이라면
자르는 순간 **회피가 사라진다.** 이 구분이 안전의 핵심이다.

## 보완 ⑥ 외력 복구 후 재개

### 사고 (2026-07-28) — 위치로 "지나왔는지"를 추정한 실수

외력 자동복구를 넣으면서, 복구 후 **남은 구간부터** 이어가려 했다.
"이미 지나온 경유점"을 판정하는 로직을 이렇게 짰다:

```python
# ❌ 잘못된 추정
if dist(다음점, 현재) < dist(다음점, 경유점):
    이미 그 구간에 들어섰다 → 경유점 버림
```

**증상**: 뚜껑 체인 `[P5, P9, P24]`를 P21에서 시작했더니 **P5·P9가 통째로 잘려 P24로 직행**했다.
회피 경유가 무효가 되어 **충돌 위험**이었다.

### 원인

**관절공간 경유점은 일직선이 아니다.**
전혀 지나오지 않았는데도 "다음 점에 더 가깝다"가 참이 될 수 있다.

```
실측: P21 기준
  P5 → P9 거리   = 78.7°
  P21 → P9 거리  = 45.6°     ← 더 가까움! → P5 를 "지나왔다"고 오판
```

### 해결 — 추정하지 말고 **기억**한다

체인이 **어디까지 명령을 보냈는지**(`at` 인덱스)를 들고 있다가, 복구 후 그 구간부터 다시 보낸다.

```python
def blend_chain(steps, ..., at=None):
    at = [0] if at is None else at
    if at[0] == 0:
        # 첫 실행에서만: 이미 그 점 위에 서 있으면 건너뜀(전환 체인 시작 처리)
        at[0] = len(steps) - len(trim_passed_steps(steps, cur))
    ...
    for i in range(at[0], len(steps)):
        at[0] = i                    # ★여기까지 명령을 보냈다
        send(amovej, steps[i])
    ...
except TripError:
    if force_recover(...):
        return blend_chain(steps, at=at)     # ★기억한 구간부터
```

**검증 결과**

| 상황 | 경로 |
|---|---|
| P21에서 뚜껑 체인 시작 | `P5 → P9 → P24` ✅ 전부 유지 |
| P5 **위에 서서** 시작 | `P9 → P24` ✅ 제자리 재이동만 생략 |
| P9로 가던 중 외력 정지 | `P9 → P24` ✅ 기억한 지점부터 |

절대목표(`mode=0`)라 재전송해도 **중복 이동도, 되돌아감도 없다.**

> 📌 **교훈**: 로봇의 진행 상태는 **추정하지 말고 기록**한다. 기하학적 추론은 관절공간에서 배신한다.

### 스플라인만은 예외

`MoveSplineJoint`는 여러 점을 **한 명령**으로 넘기므로 "어디까지 갔는지" 알 수 없다.
복구 후에는 **P5부터 순서대로** 다시 간다(절대목표라 중복 이동 없음).

## 13. 절대 지켜야 할 규칙

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | 블렌딩엔 반드시 `sync_type=1`(ASYNC) | SYNC는 블로킹이라 겹침 자체가 불가 |
| 2 | `mode=0`(절대각) 고정 | 상대이동은 재전송 시 **중복 이동** |
| 3 | 체인 중간점은 **순수 통과용만** | 회피 경유점을 넣으면 코너가 잘려 **충돌** |
| 4 | 스플라인 실행 중 `amovej` 금지 | **알람 없는 정지**(흰불) |
| 5 | 슬롯 하강은 독립 MoveJ | 스플라인에 넣으면 진입 경로가 곡선에 먹힘 |
| 6 | 마지막 점은 정식 도착 판정 | 조기 완료 → 이동 중 다음 명령 = '쿵' |
| 7 | 재개 지점은 **기억**(at), 추정 금지 | 경유점이 통째로 잘림 |
| 8 | `radius`는 async에서 무의미 | 값을 믿고 튜닝하면 시간 낭비 |

## 부록 — 왜 이렇게 오래 걸렸나

이 최적화의 대부분은 **문서에 없는 실기 동작**을 알아내는 과정이었다.

1. `radius` 파라미터가 서비스 정의에 **버젓이 있는데** 동작하지 않는다 → 드라이버 C++ 소스를 열어봐야 알 수 있었다
2. 스플라인+amovej 충돌은 **알람조차 남기지 않는다** → 재현 조건을 좁히는 데 오래 걸렸다
3. 속도가 안 나오는 게 **가속도 때문**이라는 것은 프로파일을 계산해 봐야 보였다
4. 관절공간에서 **기하학적 추론이 틀린다**는 것은 실제 웨이포인트 값으로 검산해서야 확인됐다

> 이 문서의 목적은 **같은 길을 다시 걷지 않게 하는 것**이다.
